# 误差分析（M4）

对象：e1 champion 在 val 集（280 条）上的 13 条误分 + 47 条低置信（<0.6）侥幸分对，共 **60 条人工逐条阅读**。
原始清单：`reports/val_errors_e1_word_tfidf_lr.csv`

## 错误桶（按数量排序）

| 错误桶 | 数量 | 例子 | 假设的原因 | 可能的修法 |
|---|---|---|---|---|
| ① 标注不一致 / 措辞本身歧义 | 6 | 同一文本"希望能快点修复，太影响使用了"在数据里分别被标为 bug 和 feature_request（T01402 / T00648），两个方向都错；"操作超时，不知道是崩了还是单纯慢"（T00302）——用户自己都分不清 | 人工标注无统一规范；部分工单措辞天然歧义 | **不是模型问题**。定标注规范；上线后低置信转人工 |
| ② bug ↔ performance 词汇重叠 | 4 | "…卡住相关问题"（T00080）、"…超时相关问题"（T00980）被判成 bug | "卡住/超时/卡住不动"两类共用，word 级特征粒度不够 | char n-gram（e2）；class_weight（e3） |
| ③ 零信号工单：空正文 / 极短标题 | 2 | "求助"+空正文（T01213）、"反馈一个问题"+空正文（T00618） | 文本完全没有类别信号，模型只能瞎猜 | 模型无解 → **上线规则：空文本直接转人工** |
| ④ 共享从句跨其他类对 | 3 | "扣款后功能还是用不了" billing→bug（T00401）；"登录特别慢，有时候还登不上" performance→account ×2 | 一句诉求横跨两类的真实表达 | 多标签/转人工；本期 scope 外（M1 已定单标签） |

（桶②与桶①有重叠：歧义池中 bug/performance 占大头；按主导原因归类后如上，合计 13 条误分 + 2 条边界低置信归入桶②。）

## 由误差分析驱动的迭代（做了什么、结果如何）

1. **桶② → e2（char n-gram）**：val macro-F1 0.946 → 0.960。bootstrap 检验（95% CI [+0.000, +0.031]）显示**提升不显著** → 不换 champion。桶②从 4 条缩到 3 条。
2. **桶② → e3（class_weight='balanced'）**：被拒。performance recall 涨了但 recall(bug) 从 0.959 → 0.890，逼近 0.85 红线；macro-F1 也降。零和权衡不划算。
3. **桶①③ → 非模型动作**（本次迭代最重要的结论）：
   - 给运营/标注侧提标注规范：同一措辞必须同一标签，"又慢又报错"类工单定义优先级规则
   - 上线策略：置信度 < 0.6 或文本为空的工单直接进人工队列（val 上这覆盖全部桶③和大部分桶①）

## 教训

- 13 条误分里约一半（桶①③）是**任何模型都解决不了**的——不读错误样本，就会继续在调参上浪费时间
- "涨 0.02"要先过统计显著性这道关，再谈是不是改进
