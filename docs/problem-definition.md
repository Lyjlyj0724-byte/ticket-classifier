# 问题定义：工单自动分类

> M1 产出。这份文档在写任何模型代码之前完成，是与"产品团队"对齐的结果（模拟）。

## 1. 输入 / 输出

- **输入**：工单的标题（subject）+ 正文（description），均为中文短文本；附带渠道（web/email/phone/api）与优先级（low/medium/high）两个元数据字段
- **输出**：5 个预定义类别之一：`bug` / `billing` / `feature_request` / `account` / `performance`
- **类别集合谁定的**：与产品团队对齐的结果。对齐过程中被否决的备选方案：
  - 7 类（多出的"物流""咨询"）：历史工单里这两类占比 < 3%，样本不足以支撑训练，先并入人工队列
  - 层级分类（先分大类再分小类）：第一期不做，等单级分类稳定后再评估
- **单标签**：每张工单只打一个主标签；多标签需求明确排除（见"不做什么"）

## 2. 成功指标（业务语言 → ML 指标）

业务方说法："大部分工单别分错，bug 千万别漏。"翻译成可度量指标：

| 指标 | 目标 | 理由 |
|---|---|---|
| macro-F1（val/test） | ≥ 0.75 | 类别不均衡，accuracy 会被大类灌水，必须用 macro 平均 |
| `bug` 类召回率 | ≥ 0.85 | 漏报 bug = 线上问题没人修，代价最高的错误方向 |
| `billing` 类 precision | ≥ 0.80 | 误报账单 = 财务团队白忙，第二贵 |

## 3. 失败的代价（决定优化方向）

- **最贵**：bug 被分去其他类（漏报）→ 优化 bug 的 recall
- **次贵**：其他类被误分为 billing（误报财务）→ 关注 billing 的 precision
- **相对便宜**：feature_request ↔ account 互混 → 人工改一下标签即可，容忍度高

结论：不能只看总分，必须按类别看 P/R，且 recall(bug) 是硬约束。

## 4. 基线对照（自动化的价值）

- 现状：客服人工读工单分派，约 30 秒/张，日均 500 张 ≈ 4.2 人时/天
- 自动化目标：80% 工单自动分派（置信度高的直接派），人工只看低置信度的，预计节省 3 人时/天
- 模型必须打过关键词规则基线（L0）才有存在意义——规则零成本零延迟

## 5. 不做什么（scope 边界）

- ❌ 多语言：只处理中文工单；英文工单直接转人工
- ❌ 多标签：一张工单一个主标签
- ❌ 置信度机制：低置信度转人工的阈值调优属于上线后工作，本案例只评估离线指标
- ❌ 实时性优化：批处理场景，分钟级延迟可接受，不做在线推理优化

## 6. 约束

- **可解释性**：运营偶尔会问"为什么分到这类"，选能提供特征权重的模型（线性模型可给出词权重），不用黑盒
- **成本**：CPU 可训练可推理，不引入 GPU 依赖
- **可复现**：固定 random_state，数据版本与代码 commit 绑定记录
